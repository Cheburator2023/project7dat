**2-3. Загрузка файла JSON (коммита) в очередь системы**

Цель. Пользователь хочет загрузить в систему файл коммита в формате JSON. Система должна проверить и сохранить файл обновления в своей очереди коммитов.

Предусловия. Пользователь авторизован в системе и находится в главном окне GUI.

Основной сценарий: Загрузка нового файла обновления (коммита) в очередь

1. Пользователь выбирает в основном меню главного окна системы раздел «Инкеременты», открывается окно «Очередь коммитов» с очередью несмерженных обновлений. В окне отображается список с очередью необработанных (несмерженных) загруженных файлов коммитов. Обновления отсортированы в порядке возрастания времени загрузки файла, сверху самые давние. Для каждого обновления указаны наименование, автор, статус, дата загрузки и тип файла. Не прошедшие валидацию коммиты должны быть выделены ("подсвечены") в списке коммитов.

![image.png](data:image/png;base64...)

2. Пользователь нажимает кнопку «Добавить», в открывшемся диалоговом окне выбирает локальный json файл и подтверждает его загрузку

3. Отображается модальное диалоговое окно для внесения пользователем дополнительной информации об обновлении. Пользователь заполняет в редактируемых текстовых полях диалога наименование обновления (коммита) и его описание. По умолчанию поле с наименованием заполнено именем процесса (строка до точки из desc.appName json)![image.png](data:image/png;base64...)

4. Пользователь подтверждает загрузку поименованного обновления с описанием. Диалоговое окно закрывается.

5. Фронт системы выполняет предварительные проверки загружаемого файл на соответствие формату ( json) и на максимальный размер (< 1 Мб)4.1. Ели файл не проходит предварительную проверку на фронте пользователю отображается диалоговое окно с сообщением об ошибке (РАСПИСАТЬ ПОДРОБНЕЕ). Файл не загружается. Сценарий завершается.4.2. Ели файл проходит предварительную проверку на фронте файл направляется на проверку в бэк-сервис

6. Бэк-сервис выполняет валидацию файла, сохраняет его в БД с новым уникальным идентификатором и статусом проверки. Бэкенд возвращает на фронт статус проверки файла.

6.1. Отображается диалог с и подтверждением постановки инкремента в очередь.

6.2. В конце списка очередей в окне отображается новая запись обновления с указанием его текущего статуса.

Дополнительный сценарий 1: Редактирование наименования и описания коммита из очереди

1. Пользователь выбирает запись коммита в очереди коммитов и нажимает кнопку "Править" диалога. Отображается модальное окно диалога с текущими наименованием и описанием коммита.

2. Пользователь редактирует данные о подтверждает их кнопкой "ОК"

3. Данные коммита в очереди изменились.

![image.png](data:image/png;base64...)

Дополнительный сценарий: Просмотр содержимого коммита

1. Пользователь выбирает в списке коммитов в окне коммитов запись и дважды кликает по ней мышью.

2. Отображается модальный диалог для просмотра содержимого коммита.

![image.png](data:image/png;base64...)

3. Пользователь просматривает коммит и закрывает окно диалога.

Основной сценарий: Повторная загрузка файла коммита в очередь

1. Пользователь выбирает в основном меню главного окна системы раздел «Инкеременты», открывается окно «Очередь коммитов» с очередью несмерженных обновлений.

2. Пользователь выбирает в таблице очереди запись обновления со статусом «Не прошел валидацию» и нажимает кнопку «Заменить». (файлы в статусе «прошел валидацию» заменить в очереди нельзя)

3. В открывшемся диалоговом окне выбирает локальный json файл и подтверждает его загрузку. Файл направляется на первичную проверку на фронте3.1. Ели файл не проходит предварительную проверку на фронте пользователю отображается диалоговое окно с сообщением об ошибке. Файл не загружается. Сценарий завершается.3.2. Ели файл проходит предварительную проверку на фронте файл направляется на проверку в бэк-сервис

4. Бэк-сервис выполняет валидацию файла, перезаписывает его в БД в таблице очереди обновлений с тем же уникальным идентификатором и новым статусом проверки. Бэкенд возвращает на фронт статус проверки файла. В окне списке очереди в окне обновляется статус в записи коммита.

**4-5. Мердж, сохранение обновленной модели данных**

Цель. Пользователь хочет просмотреть в системе изменения из коммита (файла JSON), подтвердить и сохранить обновления данных модели.

Предусловия. Пользователь авторизован в системе и находится в главном окне GUI. Первый в очереди коммитов файл прошел валидацию.

Основной сценарий: Обновление данных и их подтверждение пользователем

1. Пользователь выбирает в основном меню главного окна системы раздел «Инкременты», открывается окно «Очередь коммитов» с очередью несмерженных обновлений. Первый в очереди файл обновления в статусе «Прошел валидацию».

![image.png](data:image/png;base64...)

2. Пользователь нажимает кнопку «Применить». (*Не даем пользователю возможности выбирать другой коммит, потому что можно применять только первое в очереди проверенное обновление*)

3. Фронт отправляет в бэк-сервис (Parcing Service) запрос для применения инкремента к текущей версии данных. Запускается сложный процесс формирования данных на бэке.

4. Бэк сервис возвращает на фронт отвалидированный JSON файл (смерженная с коммитом текущая версия из РБД) и JSON с изменениями (Diff) (Важно! Parcing Service должен вернуть на фронт сокращенный смерженный json, содержащий не все объекты всех моделей из РБД, но только те, которые были в смерженом коммите, включая и те, которые не изменились коммитом в текущей версии).

5. Открывается окно «Merge Граф объектов имя\_процесса» с графом объектов из смерженного JSON и окно «Diff» c JSON с изменениями (Определиться с глубиной связей объектов ). В окне графов смерженных объектов все новые или измененные коммитом объекты должны быть выделены (цветом, дизайном блока, надписью статуса и т.п.) (Списки измененных объектов в отдельном окне по запросу, с возможностью перейти на объект по клику в списке ?)

6. В меню «Обновления» главного окна добавляется разделы «Подтвердить» и «Отменить».![image.png](data:image/png;base64...)

7. Пользователь просматривает в окнах в GUI и анализирует внесенные изменения. При просмотре объектов графа объектов смерженной версии все новые окна с объектами и связями открываются с наименованиями, начинающимися с «Merged »

7.1.Пользователь выбирает раздел «Подтвердить» меню «Инкременты» главного окна для подтверждения предлагаемых изменений. Фронт отправляет подтверждение принятия изменений в бэк-сервис ( Parcing Service ). Закрываются все открытые окна UI кроме главного окна. Скрываются разделы «Подтвердить» и «Отменить» меню «Обновления». Требуется очистить кэш с json файлами.

7.2. Пользователь выбирает раздел «Отменить» меню «Инкременты» главного окна для подтверждения предлагаемых изменений. Фронт отправляет отказ принятия изменений в бэк-сервис ( Parcing Service ?). Закрываются все открытые окна «Merge…» и «Diff». Скрываются разделы «Подтвердить» и «Отменить» меню «Обновления». Требуется очистить кэш с json файлами мерджа и diff.

8. Завершение сценария.

**6 Поиск объекта в DL**

Цель. Пользователь хочет найти в системе по наименованию сущность(и) определённого типа.

Предусловия. Пользователь авторизован в системе и находится в главном окне GUI.

Основной сценарий: Поиск объекта в DL

1. Пользователь выбирает в основном меню главного окна системы раздел «Поиск»

2. Открывается новое окно «Поиск»

3. Пользователь вводит наименование для одного или более типов сущностей поиска и нажимает кнопку «Искать».

4. Фронт отправляет запрос в бэк-сервис с наименованиями и типами сущностей для поиска. Бэк сервис ищет в РБД DL в соответствующих таблицах все сущности удовлетворяющие условиям поиска.

Например:

4.1 Пользователь ввел признак "А1" и нажал кнопку "Искать", сервис ищет в БД все признаки с наименованием "А1" (attribute.name)

4.2 пользователь ввел признак "А1", витрина "В2" и модель "Модель 55", сервис ищет в БД атрибут (attribute.name) "А1" для витрины (entity.name) "В2" связанной с любым вектором модели "Модель 55" (entity\_container.value).

5. Результат поиска отображается в окне поиска в табличном виде. В таблице отображаются список с описанием всех найденных в БД сущностей удовлетворяющих условиям поиска. Поля списка: наименование сущности, её тип, описание, модель, БД, процесс и его описание.

**7-9 Просмотр модели данных от объекта**

Цель. Пользователь хочет найти в системе сущности определённой модели/процесса и просмотреть их связи

Предусловия. Пользователь авторизован в системе и находится в главном окне GUI.

Основной сценарий 1: Просмотр актуальной модели данных

1. Пользователь выбирает в основном меню главного окна системы раздел «Модели»

![image.png](data:image/png;base64...)

2. Фронт направляет запрос в бэк-сервис и тот возвращает из реляционной БД системы список моделей с описанием и датами.

3. В главном окне отображается новое окно «Модели» со списком моделей и строкой для поиска модели по введённому наименованию.![image.png](data:image/png;base64...)

4. Пользователь находит в списке требуемую модель. Найденная модель выбрана(отмечена) в списке моделей.

5. Пользователь нажимает кнопку главного окна «Просмотр» или дважды кликает по выбранной модели в списке.

6. В случае, если модель была уже выбрана ранее и существует кэшированный файл JSON, используется этот файл, переход на Шаг 8. Если данные модели запрашиваются первый раз, фронт направляет запрос в бэк-сервис (Parcing Service) для запроса данных выбранной модели в формате JSON.

7. Сервис считывает из реляционной БД данные выбранной модели (входящий вектор и его аргументы), и все связанные сущности (витрины, источники с их аргументами), преобразовывает в JSON и кэширует для дальнейших запросов с фронта. Сервис возвращает в запросе JSON.

8. Фронт разбирает JSON, формирует граф объектов сущностей.

9. В главном окне отображается окно «Граф объектов имя\_модели» с графом объектов из файла JSON. модель, вектор, витрины, источники. Детализация объектов и связей вплоть до витрин и таблиц источников (аргументы не отображаются). В окне «Граф объектов» Блоки объектов различных типов различаются цветом заливки. На каждом из объектов указан его тип и наименование.

6. Фронт направляет запрос в бэк-сервис (Parcing Service) для запроса данных выбранного процесса в формате JSON.

7. Сервис считывает из реляционной БД данные выбранного процесса (источники и витрины, их атрибуты) и все их связи, преобразовывает в JSON и кэширует для дальнейших запросов с фронта. Сервис возвращает в запросе JSON.

8. Фронт разбирает JSON, формирует граф объектов сущностей.

9. В главном окне отображается окно «Граф объектов имя\_процесса» с графом объектов из файла JSON. модель, вектор, витрины, источники. Детализация объектов и связей вплоть до витрин и таблиц источников (аргументы не отображаются). В окне «Граф объектов» Блоки объектов различных типов должны различаться (цветом обрамления, заливки). На каждом из объектов должен быть указан его тип и наименование.
