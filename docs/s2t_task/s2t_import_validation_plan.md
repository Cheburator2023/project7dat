## 1. Цель и рамки
- **Цель**: дать пользователю возможность загрузить файл изменений в формате **S2T** (xlsx), просмотреть изменения и обновить данные РБД DL через существующие UI-экраны и актуальные API.
- **Входной формат**: S2T в Excel (`.xlsx`). В аналитике указано, что в названии импортируемого файла S2T с витринами **нет** лексем `json_` и `model_`.
- **Выходной формат (для импорта в DL)**: JSON в формате “коммита/инкремента” согласно схемам/требованиям.

## 3. Общий пользовательский поток (end-to-end)
### 3.1. Импорт файла S2T (xlsx)
- **Шаг 1**: пользователь выбирает файл `.xlsx` в UI.
- **Шаг 2**: FE отправляет файл на BE в endpoint “конвертация/препроцессинг” (если такой ещё не реализован — добавить), получает JSON “коммита”.
- **Шаг 3**: FE вызывает `POST /api/json-validation/validate`.
- **Шаг 4**: FE вызывает `POST /api/json-validation/check-dependencies`.
- **Шаг 5**: FE вызывает `POST /api/json-import/validate-comprehensive`.
- **Шаг 6**: если всё ок — FE вызывает `POST /api/json-import/surm` или `POST /api/json-import/dapp`.

### 3.2. Экспорт отчёта
Из аналитики `4. Экспорт данных (отчёты)`:
- В UI “Экспорт данных” пользователь выбирает формат `S2T` (xlsx) или `JSON`.
- Имя файла по умолчанию: `<schema>.<table><YYMMDDHHMM>.(xlsx|json)`.
- Ограничение: отчёт формируется только для не темповых сущностей.

## 4. Форматы данных и ответственность за конвертацию
### 4.1. Наблюдение по примерам JSON (для чтения xlsx)
В `docs/s2t_task/s2t_files_examples_jsons/*.json` лежит JSON, похожий на “дамп структуры xlsx”:
- верхний уровень: `meta`, `workbook`

**Важно**: это JSON “представление xlsx” (удобное для анализа), но **не обязательно** целевой JSON коммита, который ожидает импорт в DL.

## 5. Валидация: требования и коды ошибок
Из `1.2. Требования к валидации JSON`:
- **Полное несоответствие схеме**: вернуть **400**.
- **Проверка типов данных**:
  - ок → 200/201
  - не ок → 400
- **Частичное несоответствие схеме** (витрина без атрибутов, атрибуты к несуществующей витрине и т.п.) → **400**.
- **Ограничение на размер инкремента** (защита от загрузки всей схемы) → **413**.

Реализация в коде:
- В `apps/nestjs-server/src/modules/json-data/services/json-structure-validation.service.ts` превышение лимита размера теперь возвращает **413** (`PayloadTooLargeException`).
- **Проверка типов атрибутов и типов их использования** (where/join/etc.):
  - ок → 200/201
  - не ок → 400

**План по реализации**:
- Согласовать единый формат ошибок:
  - `code` (машиночитаемый),
  - `message` (для пользователя),
  - `path`/`entityId`/`sheet`/`cell` (если можно привязать к месту),
  - `details` (массив ошибок).
- Прокинуть ошибки в UI так, чтобы:
  - 400 показывалось как “требуется корректировка файла”,
  - 413 как “файл слишком большой (инкремент)”.

## 6. Коммиты и merging (применение инкремента)
Из `2.1. Требования к работе с коммитами`:
- “Комит” — JSON файл с метаинформацией и записями изменений.
- “Мердж” — добавление комита в основную модель.
- Есть роли сервисов: `Current Service` (инициирует мердж), `Parcing Service` (парсит в реляционную БД), `Validation Service`.

Из `3 Алгоритм применения файла коммита (merging)`:
- Описаны поля `desc.appId`, `desc.appName` и др. (мета Spark-приложения) — “только в JSON коммита”.

**План**:
- Зафиксировать domain-модель коммита:
  - мета `desc` и набор изменений (дифф по витринам/атрибутам/связям).
- Реализовать/проверить merging в соответствии с существующей доменной логикой в сервисах.
- Отдельно определить: как строится “очередь комитов” (сортировка/статусы) и какие статусы поддерживаются.
