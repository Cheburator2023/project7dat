# План рефакторинга DL UI и API

## Цели

- Обособить старый UI и старые эндпоинты, минимизировать связность с новой архитектурой.
- Спроектировать и внедрить новые (или версионированные) эндпоинты для DL.
- Постепенно перевести функциональность на новый UI и новые API без остановки сервиса.

## Этап 0. Организационная подготовка

- **Назначить владельцев**: фронт, бэк, бизнес (по сценарию из `KONST_TASK_NEW.md`).
- **Зафиксировать подход к версионированию API**:
  - предпочтительно path‑based: `/dl/api/v2/...`;
  - для критичных сценариев возможно header‑based (`X-API-Version`) или параметр `?version=2` (как исключение).
- **Определить политики совместимости**:
  - что именно гарантируем для legacy‑эндпоинтов (формат, SLA, горизонты поддержки);
  - когда и как будет происходить отключение.

## Этап 1. Инвентаризация и картирование текущего решения

### 1.1. UI (React)

- Собрать список экранов и маршрутов из `apps/react-client/src/features` (текущий UI).
- Собрать список экранов и маршрутов из `apps/react-client/src/new_features` (новый UI на моках).
- Привязать каждый экран к пользовательским сценариям из `KONST_TASK_NEW.md`:
  - Авторизация; загрузка коммита; просмотр очереди; мердж; поиск объекта; просмотр модели; changelog; DIFF и т.д.
- Зафиксировать статус по каждому экрану:
  - **legacy** (используется в проде);
  - **new** (новый UI, пока на моках);
  - **mixed** (экран использует как старые, так и новые части).

### 1.2. API / эндпоинты

- Снять список всех HTTP‑запросов фронта к бэкенду (по коду клиента и/или логам API‑шлюза):
  - метод, путь, схема запрос/ответ;
  - вызывающий экран/сценарий;
  - используемые сущности БД (по `KONST_JSON_MAPPING.md`).
- Для каждого эндпоинта определить статус:
  - **legacy** (только старый UI, старый контракт);
  - **candidate v2** (контракт логичен, нужен лишь minor‑refactor);
  - **auxiliary** (служебный, тех/health‑check и т.п.).
- Сформировать таблицу «UI → API → сущности БД» (отдельный документ/таблица).

**Результат этапа**: карта функциональности и эндпоинтов, понятный объём работ по этапам.

## Этап 2. Локализация старого UI

### 2.1. Выделение слоя legacy UI

- Ввести явный модуль/пространство имён для старого UI, например `features/legacy/*`.
- Перенести туда:
  - страницы и компоненты, которые не будут развиваться, а только поддерживаться;
  - общие компоненты, которые используются legacy‑экранами, но не нужны в новой архитектуре.
- Обозначить в коде уровни абстракций:
  - `legacy/pages`, `legacy/widgets`, `legacy/components`.

### 2.2. Маршрутизация и фича‑флаги

- В роутинге (`apps/react-client/src/routing/*`) явно разделить маршруты:
  - `legacy` маршруты (старый UI);
  - `new` маршруты (новый UI из `new_features`).
- Ввести фича‑флаги/конфигурацию для поэтапного переключения пользователей:
  - процент трафика;
  - переключение по пользователю/роли/namespace.

**Результат этапа**: старый UI выделен в отдельный слой, его проще поддерживать и постепенно отключать.

## Этап 3. Локализация старых эндпоинтов

### 3.1. Логическое выделение legacy API

- В бэкенде сгруппировать старые эндпоинты:
  - namespace типа `/dl/api/legacy/...` или `/dl/api/v1/...`;
  - отдельные контроллеры/хендлеры `Legacy*`.
- Явно задокументировать, какие UI‑экраны используют каждый legacy‑эндпоинт.

### 3.2. Стабилизация контрактов legacy

- Зафиксировать JSON‑контракты legacy‑эндпоинтов:
  - убрать «скрытые» изменения схем;
  - добавить тесты на контракты (snapshot/contract tests).
- Ввести политики изменений: только bugfix, без расширения функциональности.

**Результат этапа**: старые эндпоинты изолированы и стабилизированы, можно безопасно проектировать v2.

## Этап 4. Проектирование новых / версионированных эндпоинтов (v2)

### 4.1. Доменные модели и контракты

- На основе `KONST_TASK_NEW.md` и `KONST_JSON_MAPPING.md` сформировать целевой доменный слой API:
  - сущности DL (витрина, источник, процесс, признак и т.д.);
  - операции над ними (поиск, просмотр модели, DIFF, changelog).
- Спроектировать новые контракты под сценарии:
  - авторизация и роли (просмотр vs загрузка/мердж);
  - загрузка коммита и валидация;
  - работа с очередью коммитов;
  - построение и просмотр модели и DIFF;
  - выгрузка отчётности S2T/JSON.

### 4.2. Стратегия версионирования

- Для изменяемых эндпоинтов:
  - перенос в `/dl/api/v2/...` с чётким отличием схемы от v1;
  - поддержка параллельно v1 и v2 в переходный период.
- Для совсем новых сценариев (отсутствующих в legacy):
  - сразу добавление только v2‑версии.

#### 4.2.1. Пример: changelog v1/v2

- **Бэкенд**:
  - v1 (legacy):
    - `GET /api/changelog`
    - `GET /api/changelog/graph/:graphId`
    - используется legacy‑страницей `features/changelog/ChangelogPage`.
  - v2 (path‑based):
    - `GET /api/v2/changelog`
    - `GET /api/v2/changelog/graph/:graphId`
    - используется новым UI `new_features/changelog` (таблица + граф).
- **Фронт**:
  - `/changelog`:
    - по умолчанию — legacy‑страница (v1);
    - при флаге `featureFlags.newChangelogEnabled = true` — новая таблица (v2).
  - `/changelog-table`:
    - всегда новый UI на v2, помечен как `devOnly`.
  - API‑клиенты:
    - v1: `changelogApi` + `useChangelog` (legacy);
    - v2: `changelogV2Api` + `useChangelogV2` (новый UI).

#### 4.2.2. Пример: JSON реестр v1/v2

- **Бэкенд**:
  - v1 (legacy):
    - контроллеры `JsonDataController` (`/api/json-data`) и `JsonCommitController` (`/api/json-commits`);
    - используются текущими фичами JSON‑реестра и работы с коммитами.
  - v2 (path‑based):
    - `JsonDataV2Controller` (`/api/v2/json-data`), `JsonCommitV2Controller` (`/api/v2/json-commits`);
    - на первом шаге повторяют контракты v1 для ключевых операций реестра:
      - список JSON (`GET /list`), текущий (`GET /current`), set‑current (`POST /set-current/:id`);
      - работа с коммитами (`/commit`, `/commit/:id`, `/commits`, `/commits/all`, `/commits/search/:id`).
- **Фронт**:
  - UI `JsonDataPage`:
    - умеет работать как с v1, так и с v2;
    - переключение по фиче `featureFlags.newJsonDataV2Enabled`.
  - API‑клиенты:
    - v1: `jsonDataService` (на базе `jsonDataApi` + `jsonCommitApi`), хуки `useJsonDataList`, `useSetCurrentJsonData` и др.;
    - v2: `jsonDataV2Service` (на базе `jsonDataV2Api`), хуки `useJsonDataListV2`, `useSetCurrentJsonDataV2`.

#### 4.2.3. Пример: очерёдь коммитов v1/v2

- **Бэкенд**:
  - v1 (legacy):
    - `GET /api/json-commits/queue` в `JsonCommitController`;
    - возвращает список записей `JsonCommitEntity` со статусом `IN_PROGRESS`.
  - v2 (path‑based):
    - `GET /api/v2/json-commits/queue` в `JsonCommitV2Controller` (наследует реализацию v1);
    - на первом шаге контракт совпадает с v1.
- **Фронт**:
  - UI `CommitQueuePage` (`features/commitQueue/CommitQueuePage.tsx`):
    - раньше использовал чистые моки очереди;
    - теперь получает данные очереди через v2 API при флаге `featureFlags.newCommitsV2Enabled`.
  - API‑клиент и хуки:
    - v2: `jsonCommitV2Api` + `jsonCommitV2Service.getCommitQueue()` → `useCommitQueueV2`;
    - тип ответа `CommitQueueApiItem` (отражает `JsonCommitEntity`), маппится в `CommitQueueItem` для UI (перевод статусов, человеко‑читаемые поля).

#### 4.2.4. Пример: модели и процессы v1/v2

- **Бэкенд**:
  - v1 (legacy):
    - отдельного API для моделей/процессов нет; новый UI использует чистые моки и/или напрямую `json-data` v1.
  - v2 (path‑based):
    - `JsonDataV2Controller` (`/api/v2/json-data`) возвращает JSON‑графы в формате `DataLineageSchema`;
    - процессы и модели трактуются как представления над теми же JSON‑графами.
- **Фронт**:
  - **Процессы**:
    - `ProcessesPage` + `ProcessGraphPage` (`new_features/processes`):
      - через `useProcessesStore` под флагом `featureFlags.newJsonDataV2Enabled` получают список процессов из `jsonDataV2Service.getAll()` (каждый `JsonDataItem` маппится в `Process` с полем `dataLineage` типа `DataLineageSchema`);
      - `ProcessGraphPage` показывает граф процесса через `DataLineageGraph`, используя либо `currentProcessData` из v2, либо `process.dataLineage`.
  - **Модели**:
    - `ModelsPage` (`new_features/models/ModelsPage.tsx`):
      - раньше целиком работала на `mockModels`;
      - теперь при флаге `featureFlags.newJsonDataV2Enabled` использует `useJsonDataListV2` (`jsonDataV2Service.getAll()`) и разворачивает каждый `JsonDataItem.data.entities` (`DataLineageEntity[]`) в список `Model`, обогащённый метаданными (`authorName`, `version`, `createdAt` и т.п.).
    - `ModelGraphWindow` пока визуализирует связи на основе внутренних мок‑данных, но целевая модель — строить граф объектов и связей напрямую из `DataLineageSchema.mappings` аналогично `DataLineageGraph`.

### 4.3. Технические требования к новым эндпоинтам

- Идемпотентность, корректные коды ошибок, трейсинг/логирование.
- Ограничения по размеру JSON (с учётом требований из `KONST_TASK_NEW.md`).
- Явные связи с сущностями БД (по `KONST_JSON_MAPPING.md`).

**Результат этапа**: согласованный набор v2‑эндпоинтов с чёткими контрактами.

## Этап 5. Реализация нового UI поверх новых API

### 5.1. Завязка `new_features` на мок‑API

- Формализовать существующие моки в виде отдельного mock‑сервера или фикстур.
- Обеспечить максимально близкое соответствие моков целевым v2‑контрактам.

### 5.2. Подключение к реальным v2‑эндпоинтам

- По мере готовности v2‑эндпоинтов переключать `new_features` с моков на реальные API:
  - слой клиентских SDK/сервисов в React (одна точка входа);
  - обработка ошибок и отображение статусов.

### 5.3. Миграция сценариев

- Для каждого сценария (из `KONST_TASK_NEW.md`):
  - реализовать полный путь в новом UI (`new_features` + v2 API);
  - подключить фича‑флаг и перевести часть пользователей на новый сценарий;
  - при успешной стабилизации — перевести весь трафик и отключить соответствующие части legacy UI.

**Результат этапа**: ключевые сценарии работают в новом UI и на v2‑эндпоинтах.

## Этап 6. Переезд трафика и отключение legacy

### 6.1. Канареечный релиз и мониторинг

- Включать новый UI и v2‑эндпоинты поэтапно:
  - сначала тест/стенд, затем ограниченный процент прод‑пользователей;
  - мониторить ошибки, время ответа, нагрузку на БД.

### 6.2. Отключение legacy UI и эндпоинтов

- После успешной миграции сценария:
  - выключить фича‑флаг legacy UI;
  - закрыть доступ к привязанным legacy‑эндпоинтам (пока только внутренне);
  - через согласованный период — удалить код legacy и документацию.

**Результат этапа**: legacy‑слой выведен из эксплуатации, остаются только новые UI и API.

## Этап 7. Тестирование, качество и документация

- Покрыть ключевые сценарии e2e‑тестами:
  - загрузка/очередь/мердж коммитов;
  - просмотр модели данных, changelog, DIFF;
  - выгрузка отчётности S2T/JSON.
- Обновить документацию:
  - Swagger / OpenAPI для v2‑эндпоинтов;
  - схемы БД и JSON‑маппинг (`KONST_JSON_MAPPING.md`) при изменениях;
  - пользовательскую документацию по новым экранам.
- Настроить постоянный процесс управления изменениями API:
  - шаблон RFC для новых эндпоинтов/изменений;
  - процесс депрекации и уведомления потребителей.

---

**Итог**: после прохождения всех этапов старый UI и старые эндпоинты локализованы и постепенно выведены из эксплуатации, новая функциональность реализована на версии v2 API и новом UI с контролируемым переходом пользователей.
